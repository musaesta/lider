# Первая схема базы данных

Миграция `supabase/migrations/20261013210000_initial_store_schema.sql` задаёт
начальную схему магазина. Она подготовлена локально и **не применялась** к
удалённому проекту.

## Состав

- Профили пользователей, связанные с `auth.users`; новые профили создаются
  триггером только с ролью `customer`.
- Бренды, вложенные категории, товары, изображения по пути Storage, автомобили,
  совместимость и альтернативные артикулы.
- Корзины, позиции корзин и адреса, доступные только владельцу.
- Складской остаток и резерв как данные, но не механизм резервирования.
- Заказы с отдельными статусами заказа и оплаты, снимками адреса и контактных
  данных, позициями с неизменяемыми снимками SKU/названия/цены, историей,
  комментариями и платежами.

Товары по умолчанию неактивны, бренды и категории — не опубликованы. Публичное
чтение товаров требует активного товара и опубликованных бренда с категорией.
Отключайте товары вместо удаления: позиции заказа сохраняют собственные
снимки, а внешние ключи ограничивают удаление товара, используемого корзиной
или складом. При удалении товара, не связанного с корзинами/остатками, ссылка
из позиции заказа обнуляется, но снимок остаётся.

## Применение через Supabase CLI

Установите Docker Desktop и CLI по официальной инструкции Supabase (глобальная
установка не обязательна; ниже используется `npx`). Затем из корня проекта:

```bash
npx supabase login
npx supabase link --project-ref <PROJECT_REF>
npx supabase migration list --linked
npx supabase db push --linked --dry-run
```

Проверьте, что dry run содержит только эту миграцию и ожидаемые изменения.
Только после проверки и резервной копии базы примените её явно:

```bash
npx supabase db push --linked
```

Команда push изменяет удалённую базу. В этой задаче она **не запускалась**.
Не используйте `supabase db pull` для проекта с существующими изменениями схемы,
пока не выясните, как они соотносятся с миграциями. Перед первым push убедитесь,
что в проекте не создавались таблицы вручную и в истории миграций нет
конфликтующих версий.

Для локальной проверки на отдельной тестовой базе с работающим Docker можно
запустить `npx supabase start`, затем `npx supabase db reset`. Команда reset
пересоздаёт локальную базу и удаляет её данные; не запускайте её для удалённой
или содержащей нужные данные базы.

## Проверка после применения

В Supabase SQL Editor проверьте, что все таблицы существуют и RLS включён:

```sql
select
  c.relname as table_name,
  c.relrowsecurity as rls_enabled
from pg_class as c
join pg_namespace as n on n.oid = c.relnamespace
where n.nspname = 'public'
  and c.relkind = 'r'
  and c.relname in (
    'profiles', 'brands', 'categories', 'products', 'product_images',
    'vehicles', 'product_compatibility', 'product_cross_references',
    'carts', 'cart_items', 'addresses', 'inventory', 'orders',
    'order_items', 'order_status_history', 'order_comments', 'payments'
  )
order by c.relname;
```

Для каждой строки ожидается `rls_enabled = true`. Политики можно посмотреть так:

```sql
select tablename, policyname, roles, cmd
from pg_policies
where schemaname = 'public'
order by tablename, policyname;
```

Проверяйте сценарии через Supabase API с отдельными тестовыми аккаунтами
(анонимный клиент и два обычных пользователя):

1. Анонимный запрос видит только опубликованные бренды/категории и активные
   товары, у которых опубликованы и бренд, и категория.
2. Пользователь A видит и меняет собственные профильные поля, корзину и адреса;
   пользователь B не видит эти строки. A не может присвоить корзине пользователя
   B или добавить неактивный товар.
3. Обычный пользователь не может назначить себе `operator`/`admin`, создать или
   изменить заказ, изменить статус, создать платёж, историю статусов или
   комментарий. Пользователь видит только свои заказы, позиции и комментарии с
   видимостью `customer`; внутренние комментарии ему недоступны.
4. Пока роль не повышена, пользователь не может читать склад и не может менять
   каталог. После назначения сотрудником он может читать склад и управлять
   каталогом через RLS; записи заказов, истории, платежей и комментариев всё
   равно не предоставлены напрямую через клиентский API.

В этой миграции нет таблиц с тестовыми данными. Не делайте вывод об ошибке RLS
только по пустому результату запроса: отсутствие строк не равно отказу в доступе.
Для полного сценария заведите отдельные тестовые записи в изолированной тестовой
базе и удалите её после тестирования.

## Первый администратор

Администратор автоматически не создаётся. Сначала зарегистрируйте предназначенный
для этого аккаунт обычным способом и подтвердите его. В Dashboard найдите его
UUID в **Authentication → Users**. После применения миграции откройте SQL Editor
под ролью владельца проекта, проверьте UUID и выполните отдельный адресный запрос:

```sql
update public.profiles
set role = 'admin'
where id = '<ПРОВЕРЕННЫЙ-UUID-ПОЛЬЗОВАТЕЛЯ>'::uuid
  and role = 'customer'
returning id, role;
```

Продолжайте только если запрос вернул ровно одну ожидаемую запись. Не используйте
email из пользовательского ввода как основание для выбора аккаунта, не запускайте
массовое повышение ролей и не выполняйте этот запрос от имени обычного пользователя.
Функция для регистрации задаёт роль `customer`, а клиенту выдано право обновлять
только имя и телефон.

Последующее назначение `operator` также выполняет уполномоченный администратор
через защищённую серверную операцию или проверенное действие владельца БД.
Роли проверяются по `profiles` на стороне PostgreSQL, а не по скрытым кнопкам UI
или самостоятельно задаваемым пользовательским metadata.

## Оформление заказов и дальнейшие границы

Клиенты могут читать разрешённые заказы, но не имеют SQL-прав на их создание,
изменение, удаление и изменение статусов; аналогично закрыты прямые записи
платежей, истории, комментариев и остатков. Будущая серверная операция должна
проверять пользователя и его роль на сервере, заново получать цены и данные
доставки, рассчитывать суммы и атомарно менять остатки/резервы и создавать
заказ. Наличие `inventory` само по себе не обеспечивает резервирование.

`product_images.storage_path` ожидает путь в Storage bucket `product-images`.
Эта миграция не создаёт bucket и Storage policies: настройте их отдельно, выдавая
публичное чтение только опубликованным изображениям и запись только доверенным
серверным/сотрудническим операциям. Не помещайте `service_role` key в браузер.

## Откат

Supabase CLI не выполняет автоматически down-миграции. Миграция не содержит
команд удаления и не применялась. После появления реальных данных безопасный
путь — исправляющая миграция вперёд или восстановление проверенной резервной
копии по процедуре Supabase; не удаляйте таблицы и не помечайте миграцию
`reverted`, не выполнив реального отката схемы.

Для пустой одноразовой локальной базы допустим её полный пересозданный сброс
командой `npx supabase db reset`, но это удаляет локальные данные и повторно
применяет все оставшиеся миграции. Для пустой удалённой базы сначала сделайте
резервную копию и проверьте состояние схемы с владельцем БД; выполняйте только
отдельный, проверенный обратный SQL для объектов этой миграции. Не удаляйте
объекты удалённой базы автоматически.
